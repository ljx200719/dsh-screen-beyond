## 2. 逐项说明

### U1 · OneBot 直连的真实桥端到端（2026-11-15 已用真实桥验证 ✅）

> **2026-11-15 02:2x 实测通过**（测试桥 = 本机已在用的 SnowLuma OneBot 11 网关，端口 127.0.0.1:3000；插件只按 OneBot 11 说话，不依赖它）：
> - 插件「测试连接」→ `get_login_info` 返回在线账号（latency 约 1~4ms）；
> - 插件「发测试消息」→ 消息真的出现在对方 QQ 聊天窗口（截图确认）；
> - 对方 QQ 发一条消息 → 桥把事件 POST 到 `/api/direct-chat/event` → 她生成回复并通过 OneBot 发回对方 QQ（截图确认）。
> - 注意：这次测试桥登录的是 **aedo（你的号）**、目标是**她 VM 里的号**，角色是反的（因为 Windows QQ 上登录的是你的号）。适配器收发逻辑与真实部署一致，但“她用自己的号找你”这种正式方向还需要把桥登录到她的号（见下面说明）。
> - 顺带修了一个问题：桥重连时会回放离线历史消息，导致她突然连回好几条。现在入站会忽略 15 分钟前的旧事件（`ignored:"stale"`）。

**没验的**：只验证了一个真实桥实现（SnowLuma）；NapCat/Lagrange/go-cqhttp 等实现没有跑过（这次下载 NapCat 失败：GitHub API 看不到它的 releases、镜像 403/404；Lagrange/go-cqhttp 需要付费/授权 sign 服务，LuckyLillia 需要付费 auth token）。不同桥的字段包裹/鉴权/图片路径仍可能有差异。

**正式部署说明**：桥必须登录「她」的 QQ 号。现在 Windows QQ 登录的是你的号（aedo），所以测试时只能反着来。以后要么：① 装一个能登录她账号的 headless 桥（NapCat OneKey 等，需要能下载到）；② 或让 Windows QQ 登录她的号（会顶掉她 VM 里的 QQ）。

**原来的「没验」说明（留档）**

**已经验过**
- 适配器 `runtime/direct-chat.mjs` 对**假 OneBot 服务**的 45 项断言：`status` 成功/失败/超时/断连、`sendText` 的 body（`user_id` 数字、message 段、Bearer 头）、空 userId 拒绝、`sendImage` 的 `file:///` 与 dataURL、`parseEvent` 各种事件形状、`probeHistory` 新旧过滤、`setSettings` 校验与日志脱敏。
- 线上接口：`GET /api/direct-chat/settings` 200（19ms，状态 5 秒缓存）、桥没启动时返回中文原因（「连不上 OneBot…连接被拒绝」）。
- 入站去重、只处理私聊、只认配置的对方 QQ 号、没填对方 QQ 号不自动回复（省 token）——代码逻辑 + 单测。

**没验的**
- 没接**真的 NapCat / Lagrange / go-cqhttp**，所以不知道：
  - 不同桥的 `get_login_info` 返回包裹方式是否一致；
  - 桥的 token 认证是否就是 `Authorization: Bearer`；
  - `sendImage` 的 `file:///` 本地路径桥认不认（有些桥要 base64 或 http 链接）；
  - 真 QQ 消息往返、自动回复耗时、频控/风控表现；
  - 桥的 HTTP 上报（`/api/direct-chat/event`）字段是否与规范一致。

**怎么验（5 分钟）**
1. 本机跑一个 OneBot 11 实现（HTTP 模式开着，记下地址和 token）；
2. 面板 → 设置 → 💻VM → 「聊天软件直连」：填地址、token、**对方 QQ 号**（aedo 就是你自己），保存；
3. 点「测试连接」→ 应显示登录昵称和延迟；
4. 点「发测试消息」→ 你的 QQ 应收到一条测试消息；
5. 用你的 QQ 给机器人号发一条私聊 → 看面板聊天是否出现用户消息，并等她的自动回复到 QQ；
6. 如果哪步不对，把「测试连接」显示的报错和桥的日志发我，我按桥的实际返回改适配层。

**可能坏在哪**：桥字段形状不同（有的套一层 `data`）、鉴权方式不同、图片路径不被接受、上报地址没配好。这些都在适配器里集中处理，不用改业务代码。

### U2 · 虚拟机的自动读屏（未验，且当前环境不可用）

**已经验过**
- VM 通道的**手动坐标**路径：`POST /api/vm-chat/open {contact,row}` 按名字切会话 → `POST /api/vm-chat/send {text,composer,skipVerify}` 真发消息到 aedo，aedo（也就是你）回了「收到」。
- 视觉请求的超时修复：以前 DeepSeek 文本模型收到 `image_url` 会一直挂到 6 分钟；现在 45s/30s 超时 + 明确中文错误（「看屏幕失败：当前模型可能不支持图片…」）。
- 发送前的白名单保护：`targetContact` 配置后只对匹配会话发；没识别到会话名会再确认一次再拒绝。

**没验的 / 为什么**
- 「自动看屏幕 → 自动回复」这条链**在当前机器上跑不起来**：运行时的 `chatCompletion` 直连 `api.deepseek.com`，用的是文本模型，**不支持图片输入**。所以视觉识别本来就是不可用的，不是这次改坏的。
- 也因此没验证：视觉模型返回的坐标是否准、多窗口/多软件时选得对不对、读屏自动回复的完整闭环。

**要做的话（下一步）**：给运行时加一个**多模态模型配置**（baseUrl / key / model），让 `vm-chat` 的截图请求走它（或走 DSH 已有的多模态能力）。配好后我就能把「自动读屏 + 自动回复」真跑通；在那之前，VM 通道只能用「手动坐标」模式（面板里「立即检查 / 发测试文字」在没有视觉模型时会报明确错误，不会乱点）。

**风险**：即使配了视觉模型，坐标识别也可能出错——所以代码里保留了「发送前二次确认会话名 + 目标联系人白名单」，错发风险有兜底，但不会 100%。

### U3 · 插件自动更新的真实拉取与重启（未验）

**已经验过**
- `runtime/updater.mjs` 123 条断言：版本比较、缓存/并发、registry 各种失败、git 状态探测、apply 的 argv 断言（`git pull --ff-only`，cwd=插件目录）、dirty 拒绝、npm 安装返回 manual。
- **真实 git 端到端**（临时目录里建 bare origin + clone）：apply 真的 pull 成功，HEAD 变、版本文件从 0.7.24→0.7.25，第二次 apply 显示无变化。
- 线上 `GET /api/update/check`：真实返回 `current=0.7.24`、`latest=0.7.23`（registry 上还没 0.7.24）、`gitRepo=true`、`gitDirty=true`。
- 关于页「插件更新」卡片渲染、自动检查触发（代码 + 离屏测试）。

**没验的**
- 在**当前插件目录**真点一次「立即更新」：现在工作区有未提交改动，会**按设计**被拒绝（「有未提交的本地修改」）；这是保护，不是 bug。
- 「pull 成功 → 运行时自动退出 → 宿主用新代码重启 → 面板自动重连」整条链（临时仓库验证了 pull 部分，重启部分没跑过真实流程）。
- npm 安装形态（非 git 目录）的提示流程。

**怎么验**
1. 先把当前改动 commit（变干净）；
2. 发布一个比当前高的版本（例如 0.7.25）到 npm，或本地用 `DSH_COMPANION_NPM_REGISTRY` 指向一个能返回更高版本的测试 registry；
3. 面板 → 关于 → 「检查更新」应显示有新版 → 「立即更新」→ 观察：git pull、运行时 2 秒后退出、宿主拉起新版本、面板自动重连、版本号更新。

**风险**：非 fast-forward 冲突会拒绝并给中文说明（不会硬改代码）；重启期间面板会短暂断线几秒。

### U13 · 自写 QQ 桥（预研中，暂不可用）

> 背景：2026-11 前后，官方 QQ 生态的现成 OneBot 实现基本被清掉——NapCat 仓库/releases 已清空、Lagrange 官方签名服务关停、LLOneBot 转收费（LuckyLillia 需 Auth Token）；SnowCatQQ 等社区接力项目受 NapCat 限制性许可约束（未经作者许可不可使用/修改）。
> 方案：走「**官方 QQ 客户端注入**」路线（和 NapCat 同思路，但只做插件需要的最小子集：收私聊/发私聊/登录信息），不重写 QQ 协议、不碰 sign。
> 进度（2026-11-15 凌晨，预研第 1 步）：F: 已复制便携 QQ 9.9.37（2.3GB，不动 C 盘官方安装）、装好 LiteLoaderQQNT 1.4.1（MIT，已归档），但**卡在 QQ 文件校验**：改 `resources/app/package.json` 后启动报「文件已损坏，请重新安装QQ」。原因已定位：QQ 9.9.37 用 `resources/app/application.json` + `versions/<ver>/version.json` 里的哈希做完整性校验（当前 dbghelp.dll 劫持补丁是 2024 年的，对 9.9.37 无效）。
> 下一步：研究「更新 application.json 哈希」或更底层的注入方式；成功标准 = 注入后能收到一条真实私聊 + 发出一条真实私聊。**当前结论：不可用**，直连仍需自备可用的 OneBot 11 实现。
